# Decisiones de diseño (pendientes de revisión del dueño salvo que se indique)

Formato: ID · decisión · por qué · cómo revertirla.

- **D1-D3 (dueño, 2026-10-10)**: v0.1 incluye cliente SOAP y starter Spring Boot; importes en `BigDecimal` escala 2.
- **D4** `AeatFormat.qrAmount` quita ceros a la derecha (`241.40` → `241.4`, `241.00` → `241`). El ejemplo oficial del PDF QR v0.5.0 usa `importe=241.4` aunque la plantilla diga `NNNNNNNNN.DD`; el hash y el XML siempre llevan dos decimales. Revertir: devolver `amount()` en `VerificationUrl`.
- **D5** Codificación de la URL del QR con `java.net.URLEncoder` (UTF-8): espacio → `+`, `/` → `%2F`, `&` → `%26`. El PDF muestra el ejemplo en Java 9 con esa clase (sección 4.1, imagen no extraíble). Revertir: percent-encoding manual con `%20`.
- **D6** El modelo recorta espacios al inicio y final de cada valor al construirse (la AEAT lo hace antes de hashear) y rechaza caracteres fuera de ASCII 32-126 en `NumSerieFactura`. Nada de normalizar mayúsculas en el NIF: lo que llega es lo que se hashea.
- **D7** `RecordChain` no es thread-safe y solo guarda la cabeza (huella y fecha). Quien integra serializa con el bloqueo de su almacenamiento. Rechaza registros con predecesor distinto, más antiguos que la cabeza, o si el reloj retrocede.
- **D8** `FechaHoraHusoGenRegistro` se trunca a segundos en el constructor; el offset es el del `Clock` que recibe la cadena.
- **D9** `previousHash` externo se valida como 64 hex mayúsculas; blanco equivale a primer registro.
- **D10** Zona de silencio del QR: 4 módulos (ISO 18004); el PDF pide ≥2 mm, que depende del tamaño de impresión y queda para la maquetación de la factura, igual que los rótulos "QR tributario:" y "VERI*FACTU".
- **D11** (sesión B) El predecesor de un registro es un `ChainLink(invoiceId, hash)`, no solo la huella: el XSD v1.0 exige en `RegistroAnterior` el `IDEmisorFactura`, `NumSerieFactura` y `FechaExpedicionFactura` del registro anterior además de su `Huella`. `RecordChain` guarda ese link como cabeza y `resume()` lo recibe. Revertir: imposible sin perder la capacidad de generar XML válido; alternativa sería que el XML pidiera el ID previo aparte.
- **D12** Lo que el XML exige y la huella no cubre (`DescripcionOperacion`, `Desglose`, `Destinatarios`) vive en `InvoiceContent`, separado de `RegistrationRecord`, para que el modelo de huella siga coincidiendo 1:1 con el PDF de huella. Revertir: fundir `InvoiceContent` en `RegistrationRecord` (cambia el constructor y 20 llamadas en tests).
- **D13** Sin JAXB ni clases generadas: el XML se construye con el DOM del JDK (`VerifactuXml`) y se valida con `javax.xml.validation` contra los XSD empaquetados en `/xsd`. Cero dependencias nuevas; el orden de elementos lo garantiza el test de validación (mutación enseñada: `Huella` antes de `TipoHuella` → 3 tests en rojo). Revertir: xjc sobre los XSD y un `Marshaller`.
- **D14** `Desglose` solo soporta IVA (`Impuesto=01`) en régimen general (`ClaveRegimen=01`) con `S1`, `N1`, `N2` o exención `E1-E8`; `S2`, otros impuestos, regímenes, `IDOtro` para extranjeros y rectificativas no se modelan (se rechazan en el constructor o no existen en la API). Revertir: añadir campos a `TaxLine`.
- **D15** El cliente SOAP devuelve HTTP 500 con `Fault` como `AeatFaultException` y cualquier otro estado distinto de 200/500 como `AeatClientException`; `TiempoEsperaEnvio` solo se expone. El XSD de respuesta empaquetado (`RespuestaSuministro.xsd`) se usa en los tests para validar las respuestas del stub, porque el PDF SWeb v1.0.3 no trae cuerpos de respuesta de ejemplo para los tres estados (solo el SOAPFault, que sí se copia literal).
- **D16** `xmldsig-core-schema.xsd` se empaqueta como copia local sin su `DOCTYPE` (las entidades no se usan) y un `LSResourceResolver` lo sirve desde el classpath: la validación no toca la red (probado con proxy a un puerto muerto: `VerifactuXmlTest` 12/12 verde).
- **D17** (sesión C) El starter no tiene propiedad `verifactu.nif` aunque el contrato la citaba: ningún bean la consume (el NIF del emisor viaja en cada `InvoiceId` y en `Submission.issuer`), y una propiedad que nada lee es un camino que no hace nada en silencio. Revertir: añadir `issuer.tax-id`/`issuer.name` y un bean `Party`.
- **D18** (sesión C) Con `verifactu.enabled=true` el keystore es obligatorio: sin `key-store.path` el contexto falla con el nombre de la propiedad, en vez de crear solo la cadena. Igual con `chain.head` incompleto (los cinco valores o ninguno). Revertir: `@ConditionalOnProperty("verifactu.key-store.path")` en el bean del cliente.
- **D19** (sesión C) Un solo módulo `verifactu-spring-boot-starter` con la autoconfiguración dentro (sin módulo `-autoconfigure` aparte): dos beans no justifican dos artefactos. `Clock` se toma del contexto con `ObjectProvider` y no se registra como bean para que el starter aporte exactamente dos. Revertir: partir en dos módulos como hace Boot.
- **D20** (sesión C) El ejemplo del README vive en `ReadmeExample` (test sources) y `ReadmeExampleTest` exige que cada línea de los bloques ```java del README exista literal (sin indentación) en ese fichero; el primer bloque se ejecuta contra el stub SOAP. El segundo (certificado real) solo compila. Keystore de los tests del starter: PKCS12 vacío creado en `@TempDir`; ninguna clave en el repo.
